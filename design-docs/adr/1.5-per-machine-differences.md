# Handle per-machine differences with harness lists, pins, a home-path token, and warnings

- **Date:** 2026-11-06
- **Governs:** `/`, `harness-sync init`, `harness-sync status`, `harness-sync push`, `harness-sync pull`
- **Implementation:** pending — the sync configuration has no list of harnesses (not scheduled)

Machines differ in installed harnesses, home directory, OS, shell, and installed software, and a test machine can need
values that the other machines must not receive. Each machine lists the harnesses that it syncs, and uses one
machine-local mechanism, the pin, for partial sync and for OS-specific values. The repo has no layers.

## Decision

- **Machine-local state.** Each machine keeps its sync configuration, its base commit, and the local clone of the repo
  in `~/.harness-sync/` (`%USERPROFILE%\.harness-sync\` on Windows). Push never sends them.
- **Harnesses of the machine.** The sync configuration lists the harnesses that the machine syncs. `init` lists each
  compiled-in harness whose directory exists, unless the operator names them. `status`, `push`, and `pull` read and
  write only the items of the listed harnesses and the root files. Push leaves the repo folders of other harnesses as
  they are.
- **Pins.** A pinned item keeps its local value, and neither push nor pull moves it. Partial sync and OS-specific values
  both use pins.
- **No layers.** The repo has no OS, host, or profile layers.
- **Home-path token.** Push replaces the home directory prefix of a path in a synced JSON value with a home-path token.
  Pull expands the token to the home directory of the machine, with forward slashes on Windows. The content of a whole
  file moves unchanged.
- **Executables warn.** Pull warns when an executable that a synced command names is not on PATH. Each harness names its
  commands: Claude Code the status line, hooks, and MCP `command`; pi the MCP `command`. harness-sync installs nothing.

## Why

- The user: "pull configuration determines what to sync, so machine with claude setup, but without pi gets only claude".
- The brief: a test machine enables what the remote snapshot disables, and that change must not reach the other
  machines. Pins cover partial sync and OS-specific values with one concept.
- Absolute home paths were in 10 places on the reference machine (2026-11-04). The settings `env` block of Claude Code
  and exec-form hooks do not expand `~`, and Git Bash removes backslashes that are not in quotes.
- The user: the management of executables stays with the user, and so does a home path in the content of a file.

## Consequences

- A harness added to a machine later needs `harness add` before it syncs there. Accepted.
- Each Windows machine pins its own status line and hooks; two Windows machines repeat the same pin. Accepted.
- A pinned item gets no remote change, fixes included. Accepted.
- A home path in a whole file reaches the other machines unchanged. The user rewrites the path or pins the file.
  Accepted.

## Rejected

- **Detecting the installed harnesses on each run** — a harness whose directory is missing on one machine reads as a
  deletion of all its items, and the next push removes them from the repo.
- **OS and host layers in the repo** (Hudint/claudesync `os/<os>.json`, `hosts/<host>.json`) — a second concept for what
  pins cover.
- **File variants per OS** (FelixIsaac/claude-code-sync `name.windows.md`) — a second concept for what pins cover.
- **Installing missing executables** — the user manages the software on each machine.

## Revisit if

Users run several machines per OS that need the same overrides. Confidence: medium.
