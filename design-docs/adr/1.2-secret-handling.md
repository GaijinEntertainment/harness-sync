# Mask secrets on push and keep each machine's own value on pull

- **Date:** 2026-11-06
- **Governs:** `/`, `cc-sync push`, `cc-sync pull`
- **Implementation:** pending — the later-entry command, the TTY prompt for a missing value, and the key paths that
  the repo declares are not built (frame Phase 2)

Git history keeps every secret that a push sends, and a user can push to a public repo. cc-sync replaces each secret
with a secret placeholder on push, and keeps the real value only in the Claude Code files of each machine. The user
enters a rotated secret on each machine.

## Decision

- **Placeholder.** Push replaces each secret value with a named secret placeholder in the remote snapshot. The
  placeholder replaces the whole string value.
- **Detection.** A value is a secret when its key path matches a built-in name rule (`Authorization`, `*TOKEN*`,
  `*_KEY`, `*SECRET*`, `*PASSWORD*`, `*HEADERS*`) or a key path that the repo declares as secret.
- **Scan gate.** Before it commits, push scans the whole outgoing snapshot. Push stops when a token-like string remains
  outside a secret placeholder.
- **Pull keeps the target's value.** For a secret placeholder, pull keeps the value that the target machine already has.
  When the target has no value, pull asks for it on a TTY. Without a TTY, pull leaves the key out and lists it.
- **Later entry.** A separate command sets a missing secret on the machine from a TTY prompt or from stdin. It is the
  only command that takes a secret value.
- **Missing is not deleted.** A key that pull left out because its secret is missing is not a local deletion on the next
  push.
- **No store.** cc-sync keeps no secret store of its own and puts no encrypted secret into the repo.

## Why

- The brief: no plain-text secret in the repo; masking is the minimum; the user enters the real value on the target
  machine.
- The Claude Code files of each machine already hold the plain value. A second store adds a copy and no protection.
- Name rules miss a secret under an unexpected key, so the scan is a second check. On the reference machine, both
  secrets matched a name rule: `env.OTEL_EXPORTER_OTLP_HEADERS` and `mcpServers.<server>.headers.Authorization`
  (2026-11-04).

## Consequences

- The user enters a rotated secret on every machine. Accepted.
- A string with secret and non-secret parts, such as an `OTEL_EXPORTER_OTLP_HEADERS` value with several headers, is
  replaced whole. A change to its non-secret part does not sync. Accepted.
- A false positive of the scan blocks the push. How the user marks a value as not secret is not specified.

## Rejected

- **Encrypted secrets in the repo** (age or git-crypt: FelixIsaac/claude-code-sync, Cha1000000/claude-code-sync,
  jamie950315/ccsync) — each machine then needs the key, which is a second distribution problem. Masking meets the
  brief.
- **A secrets file per machine** (Cha1000000/claude-code-sync `ccsync-secrets.env`) — copies values that the Claude Code
  files already hold.
- **Claude Code's `${VAR}` expansion** — needs the variable in the environment of every process that starts Claude Code,
  and the settings `env` block does not expand variables.
- **Secret keys kept local and never synced** (Hudint/claudesync `localOnlyKeys`) — the key does not reach a new
  machine, so the user does not see which value to enter.

## Revisit if

Users need a secret to move between machines, for example for frequent token rotation. Confidence: high for one user
with a few machines.
