# Build a core crate, harness crates, and storage crates into one binary

- **Date:** 2026-11-07
- **Governs:** `/`
- **Implementation:** pending — the code is one binary crate (not scheduled)

harness-sync supports one harness per crate and one family of storage kinds per crate, around a core crate, and
compiles all of them into one binary. A third party adds a harness or a storage kind with a crate and builds its own
binary. Nothing loads at run time.

## Decision

- **Crates.** `harness-sync-core` holds the item model, the catalog machinery, the three-way comparison, the secret
  masking and scan, the home-path token, JSON edits, file writes, the repo settings, the sync configuration, the
  commands that return reports, and the harness and storage traits. `harness-sync-claude-code` and `harness-sync-pi`
  each describe one harness. `harness-sync-git` implements the git and Gerrit storage kinds. The `harness-sync` binary
  holds the CLI, the terminal output, the prompts, and the registry of compiled-in harnesses and storage kinds.
- **Dependency direction.** A harness crate or a storage crate depends on the core and on no other harness or storage
  crate. Only the binary depends on all of them.
- **Compile-time registry.** The binary lists the harnesses and storage kinds that it includes. A variant binary is a
  different list.
- **One workspace.** All crates live in one cargo workspace under `crates/`, share one version, and release together.

## Why

- The user: "the harness-sync core and pluggable crates that would add the support for dedicated harnesses", and
  "compiled into the binary, third parties can contribute crates or rebuild their own variant".
- Rust has no stable ABI for crates loaded at run time.
- A harness crate that cannot import another harness crate cannot convert values between harnesses
  ([1.1](/design-docs/adr/1.1-supported-items.md)).

## Consequences

- A third-party harness reaches users only in a binary that someone builds with it. Accepted.
- The core API has no stability promise for crates outside this repo. Accepted until a third party builds on it.

## Rejected

- **Run-time plugins as dynamic libraries** — without a stable ABI, the plugin and the binary need the same compiler and
  the same core build.
- **Plugins as separate processes with a protocol** — a protocol, its versions, and plugin discovery are a second
  product.
- **One crate with a cargo feature per harness** — a third party cannot add a harness without a fork.
- **Separate crates for the git and Gerrit kinds** — Gerrit differs from git only in the commit message, the
  destination ref, the change URL, and the base commit move. The user: "it is flavors".

## Revisit if

Users need harnesses that they cannot compile into their binary. Confidence: medium.
