# Number the format of the repo and of the machine-local state, and refuse a newer format

- **Date:** 2026-11-23
- **Governs:** `/`, `harness-sync.toml`, `~/.harness-sync/config.toml`
- **Pinned by:** `crates/harness-sync/tests/e2e/declarations.rs` (`a_repo_of_a_newer_format_is_refused`),
  `crates/harness-sync/tests/e2e/init.rs`
  (`a_sync_configuration_of_a_newer_format_is_refused_by_each_command_that_uses_the_state`,
  `a_sync_configuration_without_a_format_has_the_first_format`)

Builds of different ages read one repo, and a machine keeps `~/.harness-sync/` across upgrades. The repo and the
machine-local state each hold a format number, and a build refuses a number above the one that it knows. An older build
then stops with an error where it would misread the files, and that machine does not sync until it gets a newer build.

## Decision

- **Repo format.** `format` in the `harness-sync.toml` of a target numbers the format of the whole repo of that target:
  the layout of [1.14](/design-docs/adr/1.14-repo-layout.md), the secret placeholders, the home-path token, and the
  lists of the file. A repo without the file or without the key has format 1.
- **State format.** `format` in `~/.harness-sync/config.toml` numbers the format of every file in `~/.harness-sync/`.
  A file without the key has format 1. `init` writes the key, and so does each later write of the file.
- **Refusal.** A command checks the format of a `harness-sync.toml` before it reads another key of the file, and the
  format of `config.toml` before it reads or writes a file in `~/.harness-sync/`. A format above the one that the build
  knows fails the command. The error names the format and tells the operator to install a newer harness-sync.
- **New number.** A change gets a new format number when a build of the previous format would misread the files, or
  would lose data when it writes them. A new key that an older build can ignore keeps the number.

## Why

- A review before the first release (2026-11-23) found no format marker in either file. A build ignores a key that it
  does not know, and a write of `config.toml` drops such a key.
- A build that ships without the check can never refuse a later format, so the check must be in the first release. The
  user set that release: "the 0.1.0 is the target for release" (2026-11-23).
- A repo does not have to hold a `harness-sync.toml`, so an absent key needs a meaning.

## Consequences

- Each machine of a repo needs a build that knows the format of the repo. A machine with an older build runs no
  command against that repo until it is upgraded. Accepted.
- An older build ignores a new key that keeps the format number. The author of the change decides if that is safe.
  Accepted.
- harness-sync holds no code that moves a repo or a machine from one format to another, because one format exists.
  Accepted.

## Rejected

- **Refuse each key that the build does not know** — the `declarations` commands keep such keys on purpose
  (`a_change_of_one_list_keeps_the_other_lists_and_keys`), and each new key would stop every older build.
- **Require the key** — a repo without a `harness-sync.toml` has no place for it.
- **A format file of its own in the repo** — `harness-sync.toml` already holds the settings of the repo, and one more
  file at the root is one more path that is not a home file.
- **Compare the release versions of harness-sync** — a file that a person edits names no release, and a release number
  moves without a change of format.

## Revisit if

A second format needs more than one number to describe, such as a format for each harness. Confidence: medium.
