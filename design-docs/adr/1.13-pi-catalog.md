# Sync the pi catalog

- **Date:** 2026-11-07
- **Governs:** `/`, `harness-sync status`, `harness-sync push`, `harness-sync pull`
- **Implementation:** pending — the pi harness does not exist (not scheduled)

pi keeps its user-level setup in its agent directory, next to credentials, sessions, an npm tree, and caches. The pi
catalog takes the keys of its three JSON configuration files and its authored files. A setting that pi adds to
`settings.json` syncs at once, unless it is one of the three state keys that the catalog leaves out.

## Decision

- **Directory.** The pi harness reads `~/.pi/agent/`. When `PI_CODING_AGENT_DIR` is set, it reads that directory, as pi
  does.
- **`settings.json`.** Each top-level key is one item, except `lastChangelogVersion`, `trackingId`, and `deviceId`.
- **`models.json`.** Each top-level key is one item, and each entry of `providers` is one item.
- **`mcp.json`.** Each top-level key is one item, and each entry of `mcpServers` is one item.
- **Files.** `keybindings.json`, the context files (`AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`,
  `CLAUDE.MD`), `SYSTEM.md`, `APPEND_SYSTEM.md`, and each file in `extensions/`, `skills/`, `prompts/`, and `themes/`
  are items.
- **Commands.** The executables that pull checks are the MCP `command` values of `mcp.json`.
- **Never synced.** `auth.json`, `mcp-auth.json`, `models-store.json`, `trust.json`, `sessions/`, `npm/`, `bin/`,
  `mcp.log`, and the caches. `auth.json`, `mcp-auth.json`, and `models-store.json` are credentials files.

## Why

- pi's documentation lists `settings.json`, `models.json`, `mcp.json`, `keybindings.json`, the context and system
  prompt files, and the four resource directories as the files it reads at user level (pi `docs/configuration.md`,
  2026-11-07).
- The `settings.json` schema has three keys that the settings tables do not list and that hold state:
  `lastChangelogVersion`, `trackingId`, `deviceId`. All other keys are settings.
- `models.json` providers and `mcp.json` servers are independent entries, and each holds its own secrets (`apiKey`,
  `headers`, `env`).
- `models-store.json` had mode 0600 on the reference machine and appears in no document that was read (2026-11-07).

## Consequences

- A state key that a pi release adds to `settings.json` syncs until the catalog leaves it out. Accepted: the schema
  documents each key.
- A package installed from a local path lives outside the catalog. The repo's `include` list adds its directory.
  Accepted.
- `~/.agents/skills/`, which pi also reads, is not in the pi catalog; `include` adds its files as root files
  ([1.14](/design-docs/adr/1.14-repo-layout.md)). Accepted.

## Rejected

- **A list of `settings.json` keys to sync** — pi documents its settings in its schema, and a list would miss each new
  setting that a pi release adds.
- **`models.json` as one item** — two machines that change two providers make one conflict, and secrets in one provider
  hide changes to the others.
- **`packages/` in the catalog** — on the reference machine it held a local npm workspace with its own `node_modules`
  (2026-11-07), which is a build tree, not a declaration.

## Revisit if

pi stores state in `settings.json` under keys that its schema does not name. Confidence: medium.
