# Reach the remote snapshot through a storage trait

- **Date:** 2026-11-07
- **Governs:** `/`, `harness-sync init`, `harness-sync target add`, `harness-sync push`, `harness-sync pull`
- **Implementation:** pending — the commands call the git module directly (not scheduled)

The first storage kinds are git and Gerrit, and the user wants other kinds of storage later. The core reaches every
target through a storage trait with snapshots, parents, and an outcome of each publish. A new kind must keep every
snapshot that a machine can use as its base commit.

## Decision

- **Storage trait.** A storage kind fetches a target, reads the snapshot of a commit, writes a commit of file changes
  on a parent commit, and publishes a commit. Publish returns its outcome: published, sent for review, or refused
  because the remote is ahead.
- **Opaque ids.** Commit ids and file content ids are strings that the storage kind defines. The core compares them only
  for equality. The git kinds use git commit ids and blob ids.
- **Base commit.** The storage kind records the base commit of the primary target and keeps its snapshot readable. A
  published outcome on the primary moves the base commit; a sent-for-review outcome leaves it
  ([1.11](/design-docs/adr/1.11-gerrit-targets.md)).
- **Kinds.** The `kind` of a target in the sync configuration names its storage kind: `git` or `gerrit`, both in
  `harness-sync-git`.

## Why

- The user: storage "could also become crates that handle only their parts", and "such approach would give us ability
  to add support of any kind of storage in the future".
- In the code of 2026-11-07, all storage access went through one module; the snapshot was a commit and the base commit a
  ref. git and Gerrit differed in four points: the commit message, the destination ref, the change URL, and the base
  commit move.
- The three-way comparison ([1.3](/design-docs/adr/1.3-concurrent-changes.md)) reads the base snapshot after the remote
  has moved on, so a storage kind must keep earlier snapshots.

## Consequences

- A storage kind without versions, such as a plain directory, must keep its own snapshot history to fit the trait.
  Accepted.
- Only git implements the trait, so it can carry git assumptions that a second kind exposes. Accepted.

## Rejected

- **A trait of git operations** (fetch, fast-import, push with a refspec) — every other kind would have to act as git.
- **The latest snapshot only** — the three-way comparison needs the base snapshot.

## Revisit if

A second storage kind does not fit the trait. Confidence: medium.
