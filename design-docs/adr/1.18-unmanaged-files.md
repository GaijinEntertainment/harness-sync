# Keep unmanaged files in the repo, warn about them, and remove them only on request

- **Date:** 2026-11-18
- **Governs:** `/`, `harness-sync status`, `harness-sync push`
- **Pinned by:** `crates/harness-sync/tests/e2e/push.rs`
  (`push_lists_the_unmanaged_files_of_the_remote_snapshot_and_keeps_them`,
  `push_with_prune_removes_only_the_unmanaged_files`, `push_with_prune_is_refused_when_the_remote_is_ahead`)

The repo of a target can hold files that harness-sync does not manage: a `README.md` that the user keeps there, or the
files of an earlier tool or layout. harness-sync leaves them in place and warns about each, and `push --prune` removes
them. The user sees a warning for a file that they keep on purpose.

## Decision

- **Unmanaged file.** A file of a snapshot is unmanaged when it is not `harness-sync.toml`, no harness owns its path,
  and no `include` entry covers it. A file that never syncs
  ([1.1](/design-docs/adr/1.1-supported-items.md)) is unmanaged too.
- **Kept by default.** Push and the `declarations` commands leave each unmanaged file in the snapshot.
- **Warning.** Status and push list in the report the unmanaged files that the snapshot holds after the command. In
  text output they print a warning for each of these files and name `push --prune`.
- **Prune on request.** `push --prune` removes the unmanaged files of each target that it sends to, in the commit of
  that push. It makes a commit when no item changed. The push gate of
  [1.3](/design-docs/adr/1.3-concurrent-changes.md) and the secret scan of
  [1.2](/design-docs/adr/1.2-secret-handling.md) apply as they do without the flag.

## Why

- The user: "for the state when the remote happens to become dirty, the push must warn the user and suggest that if
  user wants, we could perform \"destructive sync\"" (2026-11-18).
- The first push to a repo in the layout of an earlier tool left its 22 files beside the new snapshot, and no command
  showed them (2026-11-18). [1.14](/design-docs/adr/1.14-repo-layout.md) has no migration code for that layout.
- The warning also shows a file that never syncs, such as a credentials file that a person committed to the repo.

## Consequences

- A `README.md` that the user keeps in the repo gives one warning from each status and each push. Accepted.
- `push --prune` removes every unmanaged file; it cannot keep one and remove another. Accepted.
- The git history of the repo still holds a pruned file. Accepted.

## Rejected

- **Remove the unmanaged files on every push** — a user keeps a `README.md` in the repo on purpose, and the push would
  delete it with no request.
- **Ask for confirmation in a prompt** — every command must run without a terminal
  ([1.8](/design-docs/adr/1.8-operator-interface.md)); the flag is the request.
- **Let `--prune` pass the push gate** — the gate protects the items of other machines, which the unmanaged files do not
  touch.

## Revisit if

Users keep some unmanaged files and want others removed, or the warning for a kept file becomes noise. Confidence:
medium.
