# Compare each item three ways against the base commit, and stop on conflicts

- **Date:** 2026-11-06
- **Governs:** `/`, `cc-sync status`, `cc-sync push`, `cc-sync pull`
- **Implementation:** pending — no code exists yet (not scheduled)

No machine is the master, so two machines can change the setup between pulls. cc-sync compares the local value, the
remote snapshot, and the base commit for each supported item, and lets the user pick a side for each conflict. The user
resolves two edits of one item by hand, even when the edits could merge.

## Decision

- **Base commit.** Each machine records its base commit: the remote snapshot commit that its setup last matched. A
  successful pull and a successful push both set it.
- **Three-way per item.** For each supported item, pull compares the local value, the remote snapshot value, and the
  base commit value. A change only in the remote snapshot is applied. A change only on the local machine stays for the
  next push. A change on both sides to different values is a conflict. A deletion is a change.
- **Conflicts.** The operator picks the local or the remote value for each conflict: in a prompt on a TTY, with a flag
  that names the item and the side, or with `--prefer local|remote` for all conflicts. No side wins by default.
- **No base commit.** On the first pull of a machine, every item that both sides hold with different values is a
  conflict. An item on one side only comes from that side. `pull --prefer remote` sets up a new machine in one command.
- **Push gate.** Push refuses when the remote branch has commits after the base commit. The user pulls first.
- **One comparison.** `status`, push, and pull list differences from the same comparison.

## Why

- The brief: all machines are equal, so no side is authoritative.
- A two-way comparison cannot tell an unpushed local change from a stale value, so pull would drop the change. The brief
  names lost changes as a key risk.
- Key-level items ([1.1](/design-docs/adr/1.1-supported-items.md)) keep most edits on two machines apart.

## Consequences

- Each machine stores its base commit. When it is lost, the next pull treats every difference as a conflict. Accepted.
- cc-sync does not merge inside a value. Two machines that add different rules to `permissions.deny` get a conflict.
  Accepted.

## Rejected

- **Last writer wins per key** (Hudint/claudesync) — drops the change of the earlier machine without a prompt.
- **Local wins by default** (Cha1000000/claude-code-sync) — a remote change loses on every machine that also touched the
  item, and no one sees it.
- **Overwrite with backups** (FelixIsaac/claude-code-sync, MikeVeerman/jean-claude) — the user finds a lost change only
  by reading the backups.
- **A git merge of the snapshot files** (renefichtmueller/claude-sync) — gives conflicts of JSON text lines, not a
  choice per item.

## Revisit if

Users need list values from several machines merged, for example permission rules. Confidence: medium.
